# local-bench

## Overview

local-bench is a benchmarking framework designed to evaluate local models as verified builders through isolated execution and mechanical grading. The core infrastructure consists of `bench.py`, which manages the benchmark lifecycle including model placement, chat interactions, and result recording, and `tasks.py`, which provides a suite of specific coding tasks such as deduplication, key-value parsing, and classification. A significant component of the benchmark is the multi-file Minesweeper project defined in `bench_project.py` and `minesweeper/suite.py`. This task utilizes a fixed shared data model (`minesweeper/model.py`) and a strict interface contract (`minesweeper/CONTRACT.md`) to ensure that independently generated modules for logic, rendering, and UI can compose correctly. The framework concludes with `report_grade.py`, which mechanically grades reports about the codebase itself, serving as the crux of the end-to-end (E2E) benchmark by verifying the model's understanding of the system against known parameters.

## Components

The local-bench codebase consists of several core scripts and a specialized multi-file project benchmark. The primary entry point is `bench.py`, which manages the local-model builder benchmark by defining functions for HTTP requests (`_get`, `_post`), process management (`stop_all`, `run_isolated`), and result recording (`record`, `write_summary`). Task definitions are housed in `tasks.py`, which provides a suite of classification and parsing tasks such as `c_dedupe`, `c_parse_kv`, and `c_classify`, along with grading utilities like `grade_audit` and `strip_fences`.

A distinct sub-benchmark for multi-file projects is implemented via `bench_project.py`, which handles the minesweeper task by splitting prompts, extracting files, and evaluating results. The minesweeper component itself includes a fixed shared data model in `minesweeper/model.py` (defining `Board`, `in_bounds`, `neighbors`) to ensure modular compatibility, alongside a contract specification in `minesweeper/CONTRACT.md` and an acceptance test suite in `minesweeper/suite.py`. Finally, `report_grade.py` serves as the end-to-end grader for reports about the codebase, using mechanical checks against known parameters.

## How it works

The local-bench framework evaluates local models as verified builders through two primary benchmark types: single-file task suites and multi-file project integration. The core engine in `bench.py` orchestrates the execution environment, handling model placement (local vs. cloud), isolated process runs, and result recording via HTTP-like `_get` and `_post` interfaces. It delegates specific evaluation logic to `tasks.py`, which defines a suite of atomic tasks such as deduplication, key-value parsing, classification, and provenance tracking, each graded by mechanical verdicts. For complex integration testing, the framework employs a Minesweeper clone defined in `bench_project.py`. This multi-file benchmark enforces a strict modular contract via `minesweeper/CONTRACT.md` and a shared data model in `minesweeper/model.py`, requiring candidates to generate independent `logic.py`, `render.py`, and `ui.py` modules that compose correctly. The acceptance suite in `minesweeper/suite.py` validates these components against predefined levels, while `report_grade.py` provides a mechanical grading mechanism for reports about the codebase itself, ensuring objective assessment of the end-to-end benchmark results.

## Usage and results

The local-bench suite evaluates local models as verified builders through two primary benchmarks: a general task suite and a multi-file Minesweeper project. The general benchmark (`bench.py`) executes isolated tasks defined in `tasks.py`, such as deduplication, key-value parsing, classification, and provenance tracking, recording results via the `record` function. The Minesweeper benchmark (`bench_project.py`) tests modular code generation against a fixed contract (`minesweeper/CONTRACT.md`) and shared data model (`minesweeper/model.py`), evaluating candidate implementations of logic, rendering, and UI modules using an acceptance suite (`minesweeper/suite.py`). Results are mechanically graded by `report_grade.py`, which assesses reports against known parameters to ensure objective evaluation of the benchmark outcomes.

## Limitations

The local-bench framework is constrained to evaluating local models as verified builders, which excludes cloud-based inference capabilities as indicated by the `is_cloud` check in `bench.py`. The benchmarking scope is limited to specific task suites defined in `tasks.py`, such as deduplication, key-value parsing, classification, and provenance tracking, potentially overlooking other critical builder competencies. Furthermore, the multi-file project assessment relies exclusively on a Minesweeper implementation (`bench_project.py`), where candidate modules must adhere to a rigid, pre-defined contract (`minesweeper/CONTRACT.md`) and shared data model (`minesweeper/model.py`); this restricts evaluation to modular composition within that specific domain rather than general software engineering versatility. Finally, the grading mechanism for reports (`report_grade.py`) is designed to be mechanical against known parameters, which may fail to capture nuanced or fuzzy aspects of qualitative analysis in end-to-end evaluations.
