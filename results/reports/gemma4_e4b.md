# local-bench

## Overview
local-bench is a benchmark designed for evaluating the use of local models as verified builders. The codebase is structured around several components: bench.py handles the core benchmarking logic, while tasks.py provides a suite of specific tasks (e.g., c_dedupe, c_classify). A multi-file project benchmark, minesweeper, is implemented in bench_project.py. Grading of reports, which is central to the end-to-end benchmark (E2E_PLAN.md), is managed by report_grade.py. The minesweeper task itself relies on a fixed data model in minesweeper/model.py and a strict contract defined in minesweeper/CONTRACT.md, which is tested via the acceptance suite in minesweeper/suite.py.

## Components
The codebase is structured around several key files and directories. `bench.py` serves as the main local-model builder benchmark entry point, defining core functions like `_get`, `_post`, and `main`. `tasks.py` contains a suite of specific tasks, including `c_dedupe`, `c_parse_kv`, and `grade`. `bench_project.py` handles a multi-file project benchmark, exemplified by the minesweeper task, defining functions such as `split_prompt` and `run_single`. `report_grade.py` acts as the grader for reports about the codebase, using functions like `grade_report`. The `minesweeper` directory contains critical components: `model.py`, which defines the shared `Board` data model, and `CONTRACT.md`, which specifies the implementation contract. Finally, `minesweeper/suite.py` provides the acceptance suite for the minesweeper task, running against candidate modules.

## How it works
The local-bench codebase is designed as a benchmark for evaluating local models acting as verified builders. It comprises several components: bench.py provides the core benchmarking utilities, while tasks.py defines a suite of specific tasks (e.g., c_dedupe, c_classify). For multi-file projects, bench_project.py handles benchmarks like the minesweeper task. The minesweeper task itself relies on a fixed data model in minesweeper/model.py and a strict contract defined in minesweeper/CONTRACT.md, which dictates how independently written modules must interact. Acceptance testing is managed by minesweeper/suite.py, which runs against a project structure containing the fixed model and candidate logic. Finally, report_grade.py provides a mechanical grading mechanism for reports about the codebase, particularly those referencing the E2E_PLAN.md.

## Usage and results
The local-bench codebase provides a benchmark for using local models as verified builders. Benchmarking can be performed using `bench.py` for general local-model builder tasks, or by testing specific multi-file projects like the minesweeper task via `bench_project.py`. The task suite is defined in `tasks.py`, covering various operations such as deduplication, parsing, classification, and grading. For the minesweeper task, the contract is established by `minesweeper/model.py` and `minesweeper/CONTRACT.md`, with acceptance testing handled by `minesweeper/suite.py`. Results are evaluated using `report_grade.py`, which grades reports against known parameters of the local-bench system.

## Limitations
The codebase is highly specialized for benchmarking local model builders. The grading process, particularly in `report_grade.py`, is designed to be mechanical where possible because grading reports about the codebase itself is inherently fuzzy. The `minesweeper` task relies on a fixed contract defined in `minesweeper/CONTRACT.md` and a shared, non-generatable data model (`minesweeper/model.py`), which limits the scope of what can be tested or varied outside of the defined tasks and structure.
